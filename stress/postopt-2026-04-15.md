### Homepage `GET /` — biggest single win

| | Before | After |
| --- | ---: | ---: |
| requests/s | 285 | **1 227** |
| P50 | 344 ms | 75 ms |
| P99 | 495 ms | 120 ms |
| 2xx | 5 700 / 5 700 | 24 541 / 24 541 |

`export const revalidate = 60` + middleware-based legacy-seed redirect turned the homepage from per-request SSR into ISR. First hit per 60s does server work; every subsequent hit is served from the static cache. 4.3× throughput improvement at P50 latency ÷4.

### `GET /api/counter` — kept from hitting disk

| | Before | After |
| --- | ---: | ---: |
| requests/s | 1 556 | **1 997** |
| P50 | 52 ms | 34 ms |
| P99 | 409 ms | 289 ms |

5-second TTL cache avoids `fs.readFileSync` on every hit. The counter file is only touched on writes now.

### `POST /api/randomize` — fresh generations faster

Single-seed latency dropped from ~4.5 s to ~3.5 s baseline, largely because the sprite cache is now process-global (~126 MB of disk reads per request → zero after warmup) and `UV_THREADPOOL_SIZE=4` lets the libuv pool parallelize zlib / fs ops that used to serialize.

Burst test (3 concurrent, unique seeds, single IP so only the per-IP 3/60 limit fits):
- 3 × 200, 0 × 503, 0 × 429
- Wall time: 5.1 s (vs. 3 × 3.5 = 10.5 s if fully serial) — queue + thread pool overlap confirmed

Queue depth raised from 2 → 8, so a larger burst would have queued rather than erroring. Client retries 503 once automatically with 3–6 s backoff, so transient queue pressure is invisible to users.

### Cache-hit path

Weekly challenge pre-generated on boot via `src/instrumentation.ts` → `src/lib/warmup.ts`. First request for the weekly seed after startup:

```
$ time curl -X POST -d '{"seed":31337,"weeklyChallenge":{"enabled":true,"weekOverride":1}}' http://localhost:3100/api/randomize
{"seed":31337,"status":"ready"}
real 0m0.005s   ← 5 ms
```

Verifies the "first challenge-tab viewer gets instant download" goal from the plan.

## Memory footprint

Post-warmup RSS ≈ **410 MB** (before any generations). Breakdown, roughly:
- Sprite buffers (8 classes × (12.6 MB full + 3.1 MB lowend) + panel bg) ≈ 130 MB
- Pre-generated weekly ZIP ≈ 33 MB
- Icon RGBA cache ≈ 40 MB
- Next.js + Node runtime baseline ≈ 200 MB

Each generated ZIP adds ~3–35 MB (varies by options). Cache holds ≤ 200 entries or 500 MB, whichever hits first. Steady-state in heavy use should settle around 800–900 MB — well under the 1 500 MB PM2 `max_memory_restart`.
